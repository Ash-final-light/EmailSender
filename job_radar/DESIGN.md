## 已确定的范围

全国不限城市，实习生，Unity 客户端开发；覆盖国内招聘平台和公司官网，每周两封中文邮件，沿用已验证的 QQ 发信与收信方式。

项目放入现有仓库的独立子目录，数据、主题、去重历史和发送状态独立，沿用现有仓库可见性。

毕业年份、学历、每周可出勤天数、最短实习时长尚未提供。第一版保留这些限制并突出显示，不擅自判断用户满足，也不预先排除某一届别。

## 邮件原型

建议邮件主题：【Unity实习雷达】全国客户端岗位｜统计日期范围。

分为：本期概览、已核验的匹配岗位、待核实线索、重要变更、来源与运行状态。相关 Unity 岗位为可选栏，默认关闭，避免以 XR、技术美术或纯工具岗位补足客户端岗位数量。

每条岗位的字段：

| 字段 | 展示规则 |
| --- | --- |
| 岗位名称、公司名称 | 保留原始名称，显示实体或团队信息；无法确认主体时标注 |
| 城市、具体工作地点、远程情况 | 分开记录；“全国搜索”不等于远程岗位 |
| 实习类型、面向届别和学历 | 日常/暑期/可转正等按页面原文；校招正式岗不能仅因面向学生就列为实习 |
| 薪资 | 保留数值和元/天、元/月等单位；不擅自换算，未披露写未披露 |
| 每周出勤、持续月份、到岗与截止日期 | 缺失即标未披露；刷新时间和截止时间不是同一个概念 |
| 技术与职责 | Unity/C#/客户端相关证据，以及主要职责摘要；不补写来源没有的要求 |
| 推荐理由与需核对事项 | 按已知搜索偏好解释；没有简历时不生成个人匹配分或录用概率 |
| 岗位详情链接 | 指向具体岗位；只有搜索页/招聘首页时属于线索或招聘入口，不能冒充岗位详情 |
| 公司官网链接 | 已核验域名；未知标“官网待核实”，不生成看似正确的域名 |
| 官方招聘链接 | 可与公司官网不同，招聘 SaaS 站点需核对公司官网的跳转关系 |
| 来源证据和时间 | 页面原文/平台列表/搜索摘要；首次发现、最后核验、页面发布日期分别保存 |
| 状态 | 详情可读、明确关闭、已过截止、需要登录/验证、无法确认；“可读”不直接等于正在招聘 |

目标每封最多 15 条匹配岗位，待核实线索最多 5 条。没有新增也发送简短状态邮件，并说明实际检查来源数；不会因为数量不足混入社招、过期或不相关职位。

## 接入方法

推荐采用“搜索发现 + 公司官网优先核验 + 平台公开页面补充”的混合流程。

| 来源 | 首版处理方式 | 可承诺的范围 |
| --- | --- | --- |
| BOSS 直聘 | 搜索 API 的域名定向发现，解析可公开访问的列表/详情；保留具体岗位链接 | 本次详情访问触发安全验证；受限时仅列待核实线索，不承诺全量覆盖或详情持续可读 |
| 公司官网与官方招聘站 | 优先从官网招聘入口发现，再按站点适配公开 HTML、JSON-LD 或已验证的公开接口 | 各站逐个验证，动态页面不能假定通用接口；需要登录或验证时降级 |
| 实习僧 | 搜索发现公开岗位、读取公开详情，检查已下线及截止日期 | 已观察到可读页面，也有陈旧和关闭职位；需要逐条校验 |
| 牛客招聘 | 官方职位页优先；内推/帖子仅作线索，再追溯官方详情 | 帖子不是公司官方证明，转发时间也不是岗位首次发布时间 |
| 智联/前程无忧/猎聘等 | 第二批扩展，先验证入口和提取质量 | 初版不把未经验证的平台计为已接通 |

首批公司来源候选：腾讯、网易游戏、米哈游、叠纸、莉莉丝、波克；并通过全国关键词发现其他公司。公司名单是种子，不是只搜索大厂，也不意味着这些公司当前都有匹配实习。

不执行自动投递、简历上传或与招聘方沟通；这次项目的范围是发现、核验和提醒。遇到登录、验证码或拒绝访问时记录状态，不尝试绕过。

## 为什么需要搜索 API

现有技术周报依赖新闻 RSS。招聘岗位通常不是新闻，也不保证有 RSS，因此不能直接更换几个关键词就获得可靠岗位搜索。

推荐博查官方 Web Search API，作为针对国内页面的首选待验方案；当前官方入口为 https://open.bochaai.com/，文档展示的调用域名为 api.bochaai.com。实际覆盖质量必须用用户账号试点验证，不按厂商描述假设 BOSS 数据齐全。

Tavily 作为替代方案，支持域名限制；只选择一个搜索供应商，默认不同时购买或调用两个服务。免费额度、套餐和单价以开通时页面为准，本阶段没有购买服务。

只用 DeepSeek 做文本整理不会自动获得实时互联网搜索。日常搜索消耗搜索服务调用额度，AI 归纳消耗模型 Token，两者分开记录和控制。

## 自动运行与数据状态

1. 每天 08:30 运行受限量的关键词检索和种子官网检查。
2. 提取原始字段、来源证据和时间；规则优先过滤过期、社招、非客户端。
3. 对详情和公司官网分别核验；受限、信息冲突或身份不明的留在线索栏。
4. 按岗位 ID、规范化链接、公司主体 + 标题 + 城市匹配去重；相似项保留多来源，不盲目合并不同部门或城市。
5. 每周二与周五 09:00 对新增及重要变化生成中文说明，保留事实字段。
6. 邮件发送前保存状态检查点，QQ SMTP 接受后保存发送历史；不明确的邮件投递结果阻止自动重复发送。

岗位首次发现不等于刚发布，搜索引擎抓取时间不等于发布或刷新时间。老岗位若明确开放且最近可核验，可以继续保留；“已截止/明确关闭”则移除。403、验证码、超时或单次 404 不直接解释成停止招聘。

新增、薪资/城市/届别/截止等实质变化可再次提醒；只有首次发现时发送普通提醒，避免每期重复同一批岗位。仍开放岗位保留在本地 HTML 汇总中。

使用 JSON 状态文件保存候选、公司域名核验、已提醒岗位、预算和发信状态，放在独立私有仓库。候选保留 90 天；历史记录 180 天。GitHub 定时任务可能延迟，不承诺 09:00 准时送达。

## 工具与账号

| 工具 | 用途 | 准备情况 |
| --- | --- | --- |
| Python 3.11+、requests、BeautifulSoup、Pydantic | 搜索接入、公开页面解析、结构化校验 | 可沿用现有工程经验；新项目尚未安装或实现 |
| 博查搜索 API（推荐待确认） | 全国关键词与域名定向发现岗位 | 新增依赖，需账号、API Key 和可用调用额度 |
| DeepSeek API，deepseek-flash | 只对有证据的字段归纳和排序 | 用户已有账号；新仓库仍需配置对应 Secret |
| GitHub 私有仓库 + Actions | 定时运行、日志、持久化、Artifact | 使用现有 GitHub 账号；待方案批准后创建仓库 |
| QQ SMTP | 每周两封以及额度异常提示 | 现有邮箱已验证可用；新仓库需重新配置 Secrets |
| HTML 邮件与本地 HTML 汇总 | 阅读岗位和进入详情、官网 | 已生成静态邮件样稿，尚无真实岗位数据库 |

独立仓库中的 Secrets 不会自动从 EmailSender 继承，GitHub 不提供读取原 Secret 明文的能力。待实施时配置 BOCHA_API_KEY、DEEPSEEK_API_KEY、SMTP_USER、SMTP_PASSWORD、MAIL_TO；无需把授权码写进源码。若用户更重视少配置，可改为 EmailSender 下的独立子项目，共用现有 Secrets，但不是独立仓库。

不需要域名、独立服务器、一直开机的电脑或付费招聘会员。若平台后续要求账号才能查看，应由用户在平台正常查看，不把登录依赖作为首版云端运行条件。

## Token 与额度不足时的确认机制

用户要求：用量不足时发消息说明并确认。

- 当前开发会话：若能检测到使用额度接近限制，先说明已完成事项、剩余工作及需继续的额度，再等待用户决定；账号可用百分比不等于能精确读取本次上下文剩余 Token。
- 运行中的模型：记录 DeepSeek response.usage 的实际输入/输出 Token；余额可用时通过官方余额接口辅助检查。余额与 Token 不是同一个计量单位，不凭余额推算准确剩余 Token。
- 建议初始限制：每天最多 12 次搜索 API 请求，每日最多检查 40 个详情页，每封最多 2 次模型调用、每次输出最多 5000 Token；周模型用量达到 50000 Token 时阻止下一次调用。
- 50000 是建议的累计软阈值，不是单次请求绝不会超出的费用保证。请求前用输入长度和输出上限做保守估计，记录实际值；最终阈值随方案确认。
- 即将超出已批准预算、API 明确余额不足或持续额度限制：保存进度，停止后续付费调用，发一封固定模板中文通知到现有 QQ 邮箱，不靠 AI 生成该通知。
- 通知包含原因、已处理候选数量、已有用量、剩余工作及恢复方式。不会自动充值、切换收费服务或提升预算。
- 相同问题只通知一次，等待确认；用户补足余额或明确调整预算后，通过人工恢复操作继续，不能因下次定时触发而忽略等待状态。
- 搜索 API 的余额或调用额度单独受同样规则控制。若 SMTP 本身失败，保留 Actions 失败记录与日志；不能保证通过同一个故障邮件通道通知。

## 首次验收与实施阶段

方案确认后：

1. 创建选定的仓库，接入最少一家公司官网和一个平台来源，生成真实候选样本。
2. 验证至少 20 条候选或试点期全部候选（不足 20 不凑数），检查来源详情、实习标签、城市、薪资单位、公司官网映射与失效状态。
3. 核验岗位详情受限时是否正确降级；验证搜索页不会被显示为单个具体岗位，关闭岗位不会入主列表。
4. 验证跨平台去重、岗位变化提醒、无新增邮件以及预算阻断/恢复。
5. 先发一封真实样报，由用户检查内容后再启用每周两封计划。

本次只创建方案文件、建议配置、接入验证记录和静态邮件样稿。待用户明确确认“独立仓库 + 搜索 API”或选择替代方案后，再开始以上实施。
